# pipeline — AGENTS

`golfpipe` — Python CLI turning Lantmäteriet elevation (DEM) + orthophoto GeoTIFFs into the XYZ tile pyramids the server serves (`data/tiles/{courseId}/{layer}/{z}/{x}/{y}.<ext>`).

Pure Python, self-contained venv. **No system GDAL** — rasterio wheels bundle their own. Don't add `gdal`/`pygdal` to requirements.

## Setup

```sh
# from the repo root; runs pipeline/.venv/Scripts/python.exe with cwd pipeline/
bun run py -m golfpipe --help
bun run py gspro.py --help
bun run py -m pytest    # tests — synthetic in-memory GeoTIFF fixtures, no mocks; see root TESTING.md
```

Venv missing (fresh machine): `python -m venv .venv` in `pipeline/`, then `bun run py -m pip install -r requirements.txt`. (`setup.sh` targets `.venv/bin` and python3 — Linux/macOS only.)

## Layout (`golfpipe/`)

`__main__.py` + `commands.py` (CLI) · `stac.py` (Lantmäteriet STAC search/download, needs `LANTMATERIET_USER`/`PASS`) · `raster.py`, `grid_dem.py` (LAS/LAZ lidar → DEM via laspy; `DEFAULT_CLASSES` 2, 9, 17 = ground, water, bridge deck — OPCD's CloudCompare filter, so a bridge is not a trench) · `terrain_rgb.py` (16-bit terrain PNG) · `canopy.py` (lidar nDSM → canopy height / colour ramp / DSM for the `canopy` command) · `trees_features.py` (cleaned canopy grid → tree polygons + height stats for `trees-features` / `canopy --trees-out`) · `lowveg_features.py` (`vegetation_zone` shrub proposals, source `lidar-lowveg`, for `lowveg-features`: with `--lidar` it counts returns 0.5..3 m above the ground grid per cell, `--min-points` over 3x3 cells, trees and roofs from the canopy grid, nothing within `--roof-buffer` 10 m of a roof since garden objects read as shrubs; `--canopy-tif` uses the grid's cells, which never go under 1 m; D-VZ7 in `docs/feature-vegetation-zones.md`) · `woodland_features.py` (`vegetation_zone` woodland-floor proposals, source `lidar-woodland`, for `woodland-features`: one polygon per closed stand of the canopy grid, weight from 0.5..3 m understory returns, `floorColor` sampled from the ortho between the crowns; D-VZ10) · `rocks.py` (`rock-candidates`: boulders found in the lidar, ranked with the ortho vintages; see Notes) · `woodland_floor.py` (`clean-ortho --woodland`: repaints stands as forest floor outside the corridor and `--keep` polygons) · `building_removal.py` (`gspro.py ortho --remove-buildings`: lidar roof heights from canopy `--roofs-out` plus building-survey footprints, shadow direction and length measured from the photo, holes filled from the nearest ground) · `tiling.py` (reproject → Web Mercator, XYZ pyramid) · `aoi.py`/`bbox_course.py` (area: `--bbox west,south,east,north` WGS84 **or** `--aoi file.geojson`) · `osm.py` (Overpass golf/land-cover polygons, `fetch-osm`) · `roads.py` (Overpass highway centerlines → buffered, per-class-unioned road corridor polygons, `fetch-roads`; width from the `width` tag, else `lanes`, else `CLASS_WIDTH_M`; `--near` keeps only roads within 200 m of the course features; `--centerlines-out` keeps the clipped centerlines + widths, which `road-grades` turns into one `corridor` terrain edit per road — smooth along, flat across — as the D-TE5 edits handoff) · `nvdb.py` (Trafikverket NVDB via the open data API, `TRAFIKVERKET_API_KEY`: fuses measured widths, paved/unpaved and OSM-missing roads into `fetch-roads`; OSM geometry kept, OSM-only when no key) · `buildings.py` (Overpass building footprints + minimum rotated rectangle + lidar nDSM eave/ridge heights → the building survey, `fetch-buildings`; the survey → one flat `plane` terrain edit per footprint as the D-TE5 edits handoff, `building-pads` — a building is not an app feature type, it is a pad on the terrain plus a prefab the Unity planter places) · `manifest.py` · `cleaned.py` (the cleaned photo: one 8192 px RGB GeoTIFF per site on the inner terrain square, edited in place by `cleaned-init` / `cleaned-patch` / `cleaned-replace` / `cleaned-export`; `docs/workflows.md` section 6) · `hole_cleanup.py` (`cleanup-hole` / `cleanup-compose`: trees, shadows, players and paths painted out of a copy of the cleaned photo hole by hole, by the mapped surfaces, the cleanup areas, LaMa and PhotoCraft; the rules are its constants, tuned on Vreta; `docs/photo-cleanup.md`) · `patches.py` (what those commands share with the retile under a change: `PatchError`, `bounds3006_to_3857`, `affected_tiles`).

## Vegetation rules live in `vegetation-rules/`

The planting rules of the vegetation generators and the tree chain are config, not code: `vegetation-rules/<source>.json` (`tall-grass`, `woodland-floor`, `rock-shore`, `creek-bank`, `trees` for detection + export, `arborist` for arborist.py's defaults; `tree-palette` only describes the course palette.json keys). Each rule has its value as the code had it, a unit, a line on what it does and `flag: true` when the script has a flag of that name; each file has a summary and the generator's steps in plain words. `vegetation_rules.py` binds them at import (`R = vegetation_rules.load("tall-grass")`, `DEFAULT_X = R["x"]`; the constant names stay, other modules import them). A course changes any of them under `generators.<source>` in `docs/gspro/<course>/vegetation-rules.json`: a flagged rule reaches the script as its flag (as before), any other as `--rule-overrides <json>` passed to every generator, which the loader reads from sys.argv at import (so a rule another script imports, e.g. CLEARANCES, has the course's value there too). Moving a constant into a file must leave the output byte-identical (compare every UPPERCASE constant by value and type, then dry-run the generators on Vreta and Omberg with `bun run grass:zones -- <course> --dry-run --no-export --no-arborist` and cmp the GeoJSON). The web's Planting rules panel and `bun run vegetation:rules -- <course>` show them with the course's values (server `VegetationRulesService`).

## `grass_zones.py` — tall-grass zones by rule

Whole-course `vegetation_zone` features (source `tall-grass`) from the Unity surface map
(`golfmap.surfaces.export`) or, without one, the app's features in OPCD paint order: deep rough +
Outer_Deep, a little spill into rough, within 75 m of play, clear of tees/fairways/greens/semi/bunkers/
water/blends, roads (OSM centerlines + `path`) and buildings (`fetch-buildings` survey), thinner far from
play (`Rules.far_*`, a course's nearer `Rules.near_*` multiplying with it; a course's own flags in `docs/gspro/<course>/vegetation-rules.json`). Run through
`bun run grass:zones -- <course>` (imports + re-exports zones). Rules and loop:
`.claude/skills/grass-planting/SKILL.md`; tests `tests/test_grass_zones.py`.

## `woodland_floor_zones.py` + `terrain_fields.py` — the floor under the trees by rule

`vegetation_zone` features of type `woodland_floor` with a variant (`heath`, `bilberry`, `herb`, `fern`,
and the `edge` brush as mix zones), source `woodland-floor`, from the surface map, the DEM and the planted
trees next to it (`<prefix>-<terrain>-trees.json`). `terrain_fields.py` gives slope, terrain position
(knoll or hollow) and a wetness index from a DEM; any generator can use it. The second vegetation
generator in the stack (`server/services/vegetation-generators.ts`), run by `bun run grass:zones`. Rules:
the module docs and `.claude/skills/grass-planting/SKILL.md`; tests `tests/test_woodland_floor_zones.py`,
`tests/test_terrain_fields.py`.

## `rock_shore_zones.py` — the rocky lake shore by rule

`vegetation_zone` features of type `rock_shore`, source `rock-shore`, from the surface map and the DEM next to
it: only within 40 m of the big lake (the largest water body, at least 2 ha) and on or within 10 m of a
`Slab` (12) cell, unless `--inland <0..1>` (a course's vegetation-rules.json; Omberg 0.4): then every slab, lake
or not, gets its crack and heath in full and, away from the lake, scrub and grass at that weight in a 4 m band
(`--inland-scrub-band`). Variants `crack` (texture grass and moss on the slab: noise patches favouring ledges under
30-45°, none on faces over 70°, ~35 % plus the edge fringe; mix), `heath` (sparse patches on ledges and within
3 m outside), `scrub` (bushes on land 0.5-8 m out from the slab, densest at the rock, and within 25 m of the
lake; replace, so it takes the ground from the tall rough and the floor) and `grass` (under and between the
scrub; mix). Play clearances from `grass_zones.CLEARANCES` without water and rock; paths and roads cut out.
Third in the generator stack (after the woodland floor, before the creek banks). Rules: the module doc;
tests `tests/test_rock_shore_zones.py`. The trees export keeps every stem on a `riseMode: dem` slab (a cliff
keeps its lidar scrub and low pines; `gspro.py` `_load_tree_rock_slabs`).

## `gspro.py` — GSPro/OPCD assets (not part of the tile pipeline)

Standalone CLI the server's GSPro export shells out to. Full reference: [docs/gspro/export.md](../docs/gspro/export.md).
Everything renders over one square EPSG:3006 extent (`--square-3006` verbatim from the app, or `--bbox` squared up to a 10 m side) so outputs overlay.

Layers `Hole1`…/`Others`, shapes `hole_<h>_<feature_no hex>`; `Roads` on top, every touching road/fillet/taper (of every surface) merged into one `roads_<lowest feature_no hex among its pieces>` per network (slits < 0.6 m closed, `data-feature-id` lists the pieces, no `data-surface`; OPCD needs the junction fillets dissolved in one shape, a per-surface split in the SVG was tried 2026-10-04/05 and dropped), `surface: grass` tracks written as separate shapes with the rough fill (`data-surface="grass"`, under the roads), plus the sidecar `<stem>-paths.json` (`golfmap-path-regions-v1`: `shapes` = each road shape's dominant surface, read by Unity's `golfmap.paths.materials`; `regions` = every piece with surface and outline in SVG units, for the Blender step that cuts a mixed shape's mesh along the surface seams), the sidecar `<stem>-shapes.json` (`golfmap-svg-shape-fingerprints-v1`: per SVG id 12 hex of its layer/style/fill-rule/d, for Blender's carry-over of unchanged meshes between OPCD builds; `svg-shapes <svg>...` writes it for an older SVG; never part of a name), and a rough/fairway drawn < 1 m short of a road grown to it (written flattened). **Fills are `OPCD_PALETTE` (from `OPCD Palette.gpl`) — fill colour tells OPCD what a shape is; never change those hexes.** |

## `arborist.py` — Arborist course file

Writes `arboristdata.dat` (GSPro-native vegetation): `trees`, `lower`, `lineup`, `post`, `decode`/`encode`. The server runs `lower` and `trees` at the end of the web's Update vegetation (`server/services/arborist.service.ts` finds every argument from the course; its test runs both for real on fixtures): keep their arguments and the first line each prints (`N item(s), M mask texture(s)`, `N trees of M Arborist species`) in step with it. Format, the working loop and the per-course species file: [docs/gspro/arborist.md](../docs/gspro/arborist.md).

`route` (before planting; `bun run arborist -- route <course> [--dry-run]`, `ArboristService.route`) writes `<prefix>-inner-routing.json` (golfmap-routing-v1: each tree id `own` / `billboard` / `out`) from the trees export with the tree edits applied, by the course's vegetation-rules.json `routing` (`Routing`, `FarRule`; defaults `vegetation-rules/routing.json`); it prints `own N, billboard M, left out L` (`--json` adds a last line the server reads). `--ids <id>... [--from <routing>]` routes only those trees again (the Arborist edit loop), the rest keep their routes; a routing of another trees file or other rules is routed whole. `trees --routing <file> --rules <vegetation-rules.json>` then follows it: no `"vsp"` list, no trim file; one flag without the other, or a routing whose recorded `rules` differ from the course's, is refused. Tests `tests/acceptance/test_routing_rules.py`, `tests/test_arborist_routing.py`.

## Notes

- `trees-stems` leaves out solid low objects (rocks, sheds, walls: `trees_stems.SOLID_MAX_HEIGHT_M` and the comment above it for the rule and the Vreta numbers it was set from) and writes them beside `--out` as `<out stem>-solid.geojson`: rock candidates. It needs the leaf-off ortho; `--no-kind` runs (the outer square) leave nothing out. What the detector still plants on a known rock or under a wire is dropped at export (`gspro.py trees`: `rock_slab` and `power_line` features, `--rocks`).
- `photo-stems` (`golfpipe/photo_stems.py`, rules `vegetation-rules/photo-stems.json`, tests `tests/test_photo_stems.py` and the frozen `tests/acceptance/test_photo_stems_omberg.py` on Omberg cut-outs with hand-marked trees): young trees on open ground (rough, semi, deep rough, fairway; woodland stays lidar-only) that the lidar missed, from their shadows in the summer photo, placed at the shadow's sun-side end, sized on the lidar stems that cast their own shadow there (`--lidar-size-factor` = the course's `trees.lidarSizeFactor`, so they match the scaled lidar trees), kind from the leaf-off photo. `--known <tree-stems-photo.json>` leaves the accepted and skipped ones out, by id and within `known-m`. A course's own values of these rules go under a top-level `photoStems` object in its vegetation-rules.json, not `generators` (photo stems are no vegetation generator); the server passes them as `--rule-overrides`. Accepted stems live in `data/tiles/<site>/tree-stems-photo.json`; `gspro.py trees --photo-stems` plants them with `"src": "photo"`.
- `rock-candidates` (`golfpipe/rocks.py`, tests `tests/test_rocks.py`) lists boulders standing on the ground as GeoJSON points, best first. The lidar finds them (returns 0.5-5 m over the ground model, the last of their pulse, nothing under them, single returns under open sky, squat and compact); the photos only rank them and never remove one. It uses every ortho vintage in the tiles manifest whatever its year or season (`--ortho NAME=DIR` adds one), each judged against the candidate's own surroundings in that photo, and works with none: `confidence` is `high` (grey in some vintage), `medium` (no vintage got a clear look: shadow or no photo) or `low` (seen and not grey; one step lower under a tree crown). `--near <course features GeoJSON> --near-m 35` keeps what is near play, `--buildings` drops what stands on a footprint, `--known <stone-walls.json>` marks what is already placed. It is a list to look through, not a placement: of 30 new `high` ones looked at on Vreta about 12 were rocks, the rest cars, bridges, well rings, machinery and dense bushes. It does not see rock the provider classified as ground (slabs, outcrops) or stones under 0.5 m. Thresholds are set from Vreta only (2 points/m²); check them on the next course.
- `lake-plane` (`golfpipe/lake_plane.py`, tests `tests/test_lake_plane.py`): that lake's water surface for Unity (`golfmap-lake-plane-v1`, read by `golfmap.lake.build`, which builds Lux Water planes). The shore edit's outline inside the outer square, Hydrografi's lake beyond it (fetch it for ±4.4 km round the course), out to `--radius-m` 4000 (inside GSPro's 5 km draw distance, where the horizon backdrop stands), buffered 4 m under the banks; three meshes of square cells on each other's grid lines (near 2 m over the inner square + 150 m, outer 10 m, far 25 m), a flat 5 m collider over the near part and a probe spot. Unity frame: x = E − inner west, z = N − inner south, y = level − inner minM + its position y. Write it to `<export folder>/<prefix>-inner-lake-plane.json`. Omberg: 24 km², 306k vertices, 1.2 s.
- `shore-edits` (`golfpipe/shore.py`, tests `tests/test_shore.py`): a big lake that borders the course (Omberg: Vättern) as ONE `shore` terrain edit (D-TE5, WGS84, `featherM` 0, `levelM` + the dig profile, origin `shore-edits`), its boundary the true shoreline, holes = islands and skerries. The baseline is the largest `water` polygon of a `fetch-hydro` file fetched for the outer square plus ~800 m (the dig measures distance to the edge, so the polygon must run ≥ 300 m past the outer square over open lake; it warns when not). Not the DEM: lidar has almost no returns on water and gridding fills them in, so a 10-15 m sound comes out as land. On each terrain's own DEM grid and lidar: class-2 hits above level + 0.3 m are land (closed, cut out of the 3x3-majority hydro raster), water cut off from the lake goes, specks under 1 m² without a hit go back to water; inner detail inside the inner square, outer outside it, hydro beyond. `--level` defaults to the median inner DEM over the lake shrunk by 20 m (Omberg 88.76). Use the raw `sources/dem.tif`, not an edited DEM. Omberg run: 17 s.
- `trees-stems` performance: the crown-top search used to rescan the whole grid once per plateau (quadratic; 120 of 168 s on Vreta's 2050 m square, hours on a 5 km forest square) — it now looks inside each plateau's `find_objects` box, byte-identical output, 22 s. `--tile-m N` splits the box into ~N m tiles (+30 m margin, cell-aligned) detected in a process pool and merged (stem-identical on Vreta); it is off by default because reading the LAZ files dominates and is re-done per tile while lazrs already uses every core (9 tiles: 60 s vs 22 s). Use it only for boxes where detection itself dominates.

- Areas: `--bbox` and `--aoi` are mutually exclusive. GeoJSON parsed with stdlib `json` (no fiona/pyshp); projected-CRS coords rejected.
- DEM output stays in source CRS (SWEREF99 TM / RH2000); tiling reprojects to Web Mercator once.
- Tile layers: `ortho` → `.webp` (PIL WebP q80; use `reencode_webp` to convert legacy `.jpg` trees), `terrain`, `canopy`, `surface` (Terrain-RGB) and `canopy-color` (RGBA) → `.png` (matches server `assets.service.ts` `resolveTilePath`).
